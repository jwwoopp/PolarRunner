# PolarRunner 핵심 트러블슈팅 (발표용 정리)

콘솔 ASCII 기반 pseudo-3D 러너에서 반복적으로 부딪힌 세 가지 문제를 정리했다.
세 주제는 서로 다른 증상처럼 보이지만, 근본 원인은 하나로 수렴한다.

> **화면에 그리는 좌표계와 게임 규칙을 판정하는 좌표계가 서로 다르다.**

---

## 1. IceWall 충돌 — "보이는 것"과 "맞는 것"이 다르다

### 1-1. 정규화 좌표 판정 vs 화면 ASCII 폭

**증상** — 벽이 몸에 겹쳐 보이는데 그냥 통과하거나, 반대로 여유가 있어 보이는데
`CRASH: ICE WALL`이 떴다.

**원인** — 충돌은 도로 정규화 좌표(`-1.0 ~ 1.0`)의 반폭 비교로 처리했지만,
IceWall은 거리에 따라 화면에 그려지는 폭이 **2칸 → 6칸 → 8칸**으로 달라진다.
논리 폭은 고정인데 그림 폭만 변하니 둘이 맞을 리가 없었다.

**해결** — `PolarObstacle::GetIceWallScreenBounds()`를 만들어 `Draw()`가 쓰는
근접 단계(`closeness`)와 **동일한 기준**으로 몸통 범위를 화면 좌표로 계산하고,
판정은 그 범위를 플레이어 몸통 범위와 직접 비교하도록 바꿨다.
지붕처럼 위로 갈수록 좁아지는 행은 판정에서 제외했다.

```cpp
// PolarRunner/Actor/PolarObstacle.cpp
int bodyWidth = visualVariant == 0 ? 2 : 3;
if (closeness > 0.72f)      { bodyWidth = 8; bodyRowSpan = 2; }
else if (closeness > 0.30f) { bodyWidth = 6; bodyRowSpan = 1; }
```

### 1-2. 커브 구간에서만 나는 오충돌

**증상** — 직선에서는 정상인데 커브에서 벽을 피했는데도 충돌했다.

**원인** — 판정 코드가 **플레이어의 Y행**에서 벽의 X를 다시 투영했다.
커브에서는 Y행마다 도로 중심이 다르기 때문에, 벽이 실제로 그려진 위치와
판정용 위치가 어긋났다.

**해결** — 벽의 X는 `Draw()`와 똑같이 **벽 자신의 Y행**에서 계산한다.

### 1-3. 짝수 폭 off-by-one

**증상** — 벽 오른쪽에 "보이지 않는 한 칸"이 있어서 스치지도 않았는데 죽었다.

**원인** — `center ± halfWidth`로 범위를 잡았는데, 폭이 짝수(8칸/6칸)이면
`Draw()`가 실제로 출력하는 `x - len/2 ~ x - len/2 + len - 1`보다 오른쪽이 한 칸 넓다.

**해결** — 문자열 길이 그대로 끝 좌표를 구한다.

```cpp
bounds.left  = x - bodyWidth / 2;
bounds.right = bounds.left + bodyWidth - 1;   // center + half (X)
```

### 1-4. 점프 자세의 히트박스가 밀림

**증상** — 왼쪽을 보며 점프할 때만 충돌 판정이 화면보다 오른쪽으로 2칸 밀렸다.

**원인** — 미끄러지는 자세 몸통 `(_____)`는 방향에 따라 `x-5` 또는 `x-1`에서 시작하고,
점프 자세 몸통 `/( _ )\`는 방향과 무관하게 `x-3`에서 시작한다.
판정은 항상 미끄러지는 자세 오프셋만 썼다.

**해결** — `Player::GetBodyLeftOffset()` / `Player::BodyWidth`를 만들어
`Draw()`와 판정이 **같은 값을 공유**하고, 점프 중에는 점프 몸통 오프셋을 쓴다.
부리(`>` `<`)와 미끄러짐 잔상(`____`)은 히트박스에서 제외했다.

```cpp
// PolarRunner/Level/PolarLevel.cpp
const int playerBodyLeft = playerCollisionX
    + (player->IsJumping() ? -3 : player->GetBodyLeftOffset());
const int playerBodyRight = playerBodyLeft + (Player::BodyWidth - 1);
```

### 1-5. 멀리 있는 벽과 조기 충돌 (가장 중요한 원인)

**증상** — 점프하면 아직 멀리 있는 IceWall과 충돌했다.

**원인** — 세로 판정을 **화면 Y의 AABB 겹침**으로 했다. 그런데 화면 Y에는
서로 다른 두 의미가 섞여 있다.

| 대상 | 화면 Y의 의미 |
|---|---|
| 장애물 | 진행 거리(`distance`)를 원근 투영한 결과 |
| 플레이어 | 진행 위치 + **점프 연출 오프셋** |

즉 "점프해서 위에 그려진 것"을 "앞으로 전진한 것"으로 오해했고,
높이가 큰 IceWall ASCII와 화면에서 겹치기만 해도 충돌했다.

**해결** — 충돌 시점을 도형의 겹침이 아니라
**장애물이 플레이어의 진행선을 통과하는 순간(swept row crossing)** 으로 바꿨다.

```cpp
const bool crossedPlayerRow =
    previousObstacleScreenY <= currentPlayerScreenY
    && obstacleScreenY >= currentPlayerScreenY;
```

이전 프레임 행과 현재 프레임 행 사이를 검사하므로, 속도가 빨라
한 프레임에 여러 행을 건너뛰어도 충돌을 놓치지 않는다.

**판정 순서**
1. 장애물이 플레이어 진행선에 도달했는가 (세로)
2. 그 순간의 몸통 가로 범위가 겹치는가 (가로)
3. 장애물별 회피 조건(점프 높이 등)을 만족하는가
4. 모두 참이면 Crash, 진행선을 지나면 `MarkChecked()`

## 2. 맵 원근감 — 한 장의 화면에 두 개의 좌표계

### 2-1. 투영 공식

거리 → 화면 행은 비선형(`pow 1.55`) 으로 압축한다. 선형이면 멀리 있는 물체가
너무 빨리 다가와 속도감이 죽는다.

```cpp
// distance -> screen row
const float normalized  = clamp(1.0f - distance / viewDistance, 0.0f, 1.0f);
const float perspective = pow(normalized, 1.55f);
return roadTopY + int(perspective * (roadBottomY - roadTopY));

// screen row -> distance (역함수)
const float normalized = pow(ScreenYToRoadDepth(screenY), 1.0f / 1.55f);
return (1.0f - normalized) * viewDistance;
```

### 2-2. 커브가 "가로 지퍼"로 보이던 문제

**증상** — 커브가 급해지면 도로 경계선이 계단이 아니라 가로줄처럼 찢어져 보였다.

**원인** — 초기 구현은 이전 행과 현재 행의 경계점을 잇는 방식(`DrawRoadBoundary`)이었다.
한 행에 한 칸만 찍으니, 행 간 X 차이가 여러 칸이면 그 사이가 비었다.

**해결** — 경계선을 잇는 대신 **모든 행에서 `CalculateRoadSlice(depth)`를 계산**해
그 행의 중심·반폭으로 지형을 채우는 구조로 바꿨다. 렌더는 행 단위로 독립적이다.

### 2-3. 지평선에서 커브가 접혀 보이는 문제

**증상** — 먼 거리의 도로가 좌우로 크게 흔들려 지평선이 접히는 것처럼 보였다.

**원인** — 커브 오프셋을 깊이와 무관하게 적용했다. 실제 원근에서는 먼 곳일수록
횡방향 이동이 작게 보여야 한다.

**해결** — smoothstep으로 먼 행의 횡이동을 억제해, 커브가 지평선에서 **자라 나오도록** 했다.

```cpp
const float curvePerspective = depth * depth * (3.0f - 2.0f * depth); // smoothstep
const float maximumCurveOffset = screenWidth * 0.18f;
slice.centerX = screenWidth / 2
    + int(slice.centerOffset * curvePerspective * maximumCurveOffset);
```

### 2-4. 도로 폭이 화면 밖으로 나가거나 갑자기 좁아지는 문제

**해결** — 세 겹의 안전장치를 뒀다.

- `maximumVisibleHalfWidth` : 커브로 중심이 밀려도 화면 밖으로 새지 않도록 클램프
- `widthBlend`(smoothstep) : 지형 폭 변화가 특정 행에서 툭 튀지 않게 블렌딩
- 지형별 `minimumWidthScale` : Canyon `0.45`, NarrowIcePath `0.28` — 좁아도 최소 통행 폭 보장

### 2-5. 정수 화면 좌표가 만든 판정 오차

콘솔은 행이 정수라 원근 투영 결과가 반올림된다. 여기서 두 종류의 버그가 나왔다.

- **역변환 판정 실패** — 플레이어 화면 행을 거리로 되돌려 비교했더니, 실제로
  그려지는 행 경계와 어긋나 충돌을 통째로 놓쳤다.
  → 변환은 **거리 → 행 한 방향**만 쓰고, 행 통과 여부(swept)로 판정.
- **BrokenBridge 물 행 위치** — 원근 단계에 따라 물 행이 `y-1`(가까움) / `y`(중간)로 달라지는데
  판정은 항상 `y-1`을 썼다. → `Draw()`와 같은 `closeness` 임계값을 판정에서도 사용.

```cpp
const auto getBridgeWaterScreenY = [this](float distance, int screenY)
{
    const float closeness = 1.0f - distance / viewDistance;
    return closeness > 0.80f ? screenY - 1 : screenY;   // Draw()와 동일 기준
};
```

또한 고속에서 다리를 한 프레임에 여러 행 지나쳐 Crash 화면에서 다리가
펭귄 아래에 떨어져 보이는 문제는, **판정은 swept로 유지하고 표시용 거리만**
접촉 행으로 고정해 해결했다.

### 2-6. 전투가 맵을 덮어쓰던 문제

**증상** — Enemy가 등장/제거될 때 지형이 다른 맵으로 순간 교체되는 것처럼 보였다.

**원인** — 렌더링 코드가 Enemy 생존 여부를 보고 **모든 `RoadSlice`의 지형을 `Coast`로 강제**했다.
실제 코스 데이터와 화면이 달라진 것이다.

**해결**
- 화면 지형은 **항상 `CalculateRoadSlice()`가 반환한 코스 데이터만** 사용한다.
- Enemy 등장 판단은 해안 구간 안에서만 한다. 바다의 좌우 방향도 구간 데이터로 결정한다.
- Enemy가 제거되는 **그 프레임**만 예외로 해안을 유지한다
  (`coastEnemyWasActive` + `coastVisualHoldTimer`). Actor 충돌 처리가 Level Tick 이후에
  일어나 한 프레임 깜빡임이 생겼기 때문이다.

> **정리** — 게임 규칙은 논리 좌표(거리·정규화 X)로, 화면 좌표는 렌더링에서만.
> 단, "화면에 보이는 것"을 판정해야 하는 IceWall 같은 예외는
> **렌더와 판정이 같은 함수를 공유**하게 만든다.

## 3. 슈팅 요소 — 러너에 전투를 얹으면서 생긴 문제들

### 설계 요약

| 요소 | 규칙 |
|---|---|
| 탄약 | 별 `5`개 수집 → `SHOT` 1발 (`RequiredStarCount = 5`) |
| 발사 | `F` 키, 바라보는 방향으로, 점프 중에는 불가 |
| 적 | 해안(Coast) 구간에서 바다 쪽으로 등장 → 측면 접근 → 추격 사격 |
| 스폰 조건 | `SHOT`이 0발이면 아예 등장하지 않음 (반격 불가 상황 차단) |

### 3-1. 스폰 직후 즉사하는 탄환 (엔진 버그)

**증상** — 화면 오른쪽에서 스폰된 Enemy가 접근하지도 않았는데
`CRASH: HIT BY ENEMY BULLET`이 떴다. 왼쪽 스폰에서는 덜 발생했다.

**원인** — `Craft::Actor` 생성자가 `previousPosition`을 초기화하지 않아 `(0,0)`으로 남았다.
충돌 판정은 이전 위치 → 현재 위치를 잇는 **swept 선분**을 쓰므로, 스폰 첫 프레임에
화면 왼쪽 위에서 스폰 지점까지 **화면을 가로지르는 거대한 선분**이 생겼다.
오른쪽에서 스폰될수록 이 선분이 플레이어를 지날 확률이 높아 증상이 두드러졌다.

```cpp
// CraftEngine/Actor/Actor.cpp
Actor::Actor(const std::string& image, const Vector2& position, Color color)
    : image(image), position(position), previousPosition(position),  // 추가
      color(color), width(static_cast<int>(image.size()))
{ }
```

같은 `Test()`를 쓰는 PlayerBullet–Enemy 충돌에도 잠재적 영향이 있던 **공용 버그**였다.

### 3-2. 탄환이 커질 때 중심이 어긋나던 문제

플레이어 탄환은 날아간 거리에 따라 `*` → `<>` → `<#>`로 커져 원근감을 준다.
그런데 Actor 위치 기준은 문자열의 **왼쪽 끝**이라, 이미지가 커질수록 궤도가 한쪽으로 밀렸다.

```cpp
// 이미지가 커져도 탄환 중심이 이동 경로에 맞도록 보정
newPosition.x = static_cast<int>(xPosition) - GetWidth() / 2;
```

### 3-3. 적이 육지에 떠 있던 문제 (좌우 스폰)

처음에는 접근 위치·정차 위치·발사 방향이 모두 **왼쪽 스폰 전제로 하드코딩**되어 있었다.
좌우 대칭으로 일반화하면서 선체 ASCII를 좌우 반전해 포문이 도로를 향하게 하고,
`EnemyBullet`도 왼쪽 경계(`x <= 0`)에서 소멸하도록 고쳤다.

이후 랜덤 스폰은 다시 **배경(바다)이 그려지는 방향**(`coastOceanOnRight`)과
일치시키도록 바꿨다. 랜덤만 쓰면 배가 눈밭 위에 떠 있는 화면이 나왔기 때문이다.

### 3-4. 전투가 지형을 넘어 따라오던 문제

격추하지 못한 채 해안을 벗어나면 배가 눈밭에서도 계속 추격했고,
이미 발사된 탄환은 지형이 바뀐 뒤에도 플레이어를 맞혔다.
→ `terrain != Coast`가 되면 Enemy와 **잔여 탄환까지 함께 정리**한다.

### 3-5. 전투와 좁은 얼음길이 겹쳐 난이도가 폭발하던 문제

탄환을 피하면서 미끄러운 좁은 길까지 통과해야 하는 구간이 생겼다.
렌더링에서 지형을 잠깐 숨기는 방식은 2-6과 같은 화면 불일치를 다시 만들기 때문에,
**맵은 그대로 두고 전투 쪽 스케줄을 조정**했다.

- 앞 `220m` 안에 `NarrowIcePath`가 있으면 **신규 스폰 금지**
- 활성 Enemy가 Slip `120m` 앞까지 남아 있으면 **후퇴 + 기존 탄환 제거**
- 의도적 후퇴에서는 해안 유지 타이머를 시작하지 않아 다음 지형을 가리지 않음

### 3-6. 피격 판정을 자세별로 분리

```cpp
const int playerLeft  = playerX - (player->IsJumping() ? 3 : 5);
const int playerRight = playerX + (player->IsJumping() ? 3 : 5);
const int playerTop   = playerY - (player->IsJumping() ? 4 : 1);
```

탄환은 X축으로 빠르게 이동하므로 이전~현재 X를 합친 swept 범위로 검사해
프레임 사이 관통(tunneling)을 막았다.

### 3-7. 사격 난이도 튜닝

- 고정 `2.0`초 간격 → **예고탄 / 빠른 후속탄 / 긴 휴식** 3패턴 반복으로 변경
- 진행률 비례 스케일링은 초반부터 너무 매웠다 → 거리 구간 테이블로 교체

| 구간 | 발사 간격(초) |
|---|---|
| 0 ~ 5,000m | 3.8 / 3.2 / 4.2 |
| 5,000 ~ 10,000m | 3.0 / 2.1 / 3.4 |
| 10,000m ~ | 2.4 / 1.5 / 2.8 |

## 검증 방법 — 눈으로 못 보는 건 로그로 본다

판정 버그는 재현이 어려워, 플레이 중 이벤트를 자동으로 남기게 했다.

```cpp
// [1234.5m] CRASH: ICE WALL speed=28 playerX=[41,47] wallX=[44,51]
LogEvent("...");   // PlaytestLog.log
```

- 크래시 시 **판정에 실제로 쓰인 좌표**(플레이어 몸통 / 벽 몸통)를 함께 기록
- BrokenBridge는 `jumpHeight`, `jumpOffset`을 기록해 높이 기준 논쟁을 데이터로 정리
- 코스 생성 단계에서 **IceWall이 세 레인을 모두 막는 조합**을 자동 경고
- 100m마다 속도 체크포인트를 남겨 밸런스 곡선을 확인

## 마무리: 세 문제의 공통 교훈

1. **그리는 코드와 판정하는 코드가 좌표를 각자 계산하면 반드시 어긋난다.**
   → 공유 게터(`GetBodyLeftOffset`)나 공용 함수(`GetIceWallScreenBounds`)로 단일 기준을 만든다.
2. **화면 좌표에는 여러 의미가 섞인다.** 원근 투영 + 연출 오프셋이 한 값에 들어가면
   "위에 그려진 것"과 "앞으로 간 것"을 구분할 수 없다.
3. **연출을 위해 데이터를 덮어쓰지 않는다.** 전투 때문에 맵을 바꾸는 대신,
   전투 스케줄을 맵에 맞춘다.
