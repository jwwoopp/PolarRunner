## 2. ⚠️ 먼저 결정해야 할 것 — 코스 거리 표기

**현재 슬라이드는 "5000m"라고 되어 있지만 코드와 맞지 않습니다.**

```cpp
float courseDistance = 15000.0f;                              // PolarLevel.h
constexpr float finalDistanceKm = 20004.0f;                   // 표시용 최종 거리
hud << "DISTANCE: " << displayDistance / 1000.0f << " km";    // HUD는 km 단위
```

- 내부 코스 길이는 **15000** (5000 아님)
- HUD는 m가 아니라 **km**로 표시되며 최종 **20004 km**까지 올라감
- Enemy 구간 정의도 `14770.0f`까지 존재

**시연 영상에서 HUD에 `DISTANCE: ... km`가 표시되므로, 슬라이드의 "5000m"와 어긋납니다.**

> **작성자 확인 필요**: 아래 중 하나로 통일하세요.
> - (A) `15000m 코스` — 내부 값 기준
> - (B) `20004km 완주` — HUD 표시 기준 (남극점 스케일 연출)
> - (C) 거리 수치를 빼고 `남극 종단 코스`처럼 표현
>
> 이 문서에서는 임시로 **`[코스거리]`** 로 표기합니다. 결정된 값으로 치환해 주세요.
> 해당 위치: 슬라이드 2 본문, 슬라이드 6 흐름도 마지막 박스(`5000m Goal`)

### 슬라이드 2 — 프로젝트 개요

#### 삭제

**우측 하단 "플레이 흐름" 흐름도 6개 박스를 통째로 삭제합니다.**
(`달리기 → 장애물 회피 → 별 수집 → 사격 → 해안 전투 → 완주`)

삭제 이유:
1. 바로 위 한 줄 요약과 내용이 중복됨
2. 좌측 게임 스크린샷이 같은 정보를 훨씬 잘 전달함 (펭귄·장애물·별·밀렵선이 모두 보임)
3. 박스가 좁아 `달리 / 기`, `사 / 격`, `완 / 주`처럼 글자가 세로로 쪼개져 있고,
   6개가 2줄로 접혀 흐름이 오른쪽 끝 → 왼쪽 끝으로 역행하는 모양이라 흐름도 기능을 못 함
4. 슬라이드 11에 시연 영상(4~5분)이 있어 플레이 흐름은 영상이 담당

#### 추가

### 슬라이드 4 — 개발 환경과 구조 ★ 최우선

> **이 슬라이드가 "엔진을 어떻게 보완했는지" 피드백의 핵심 대상입니다.**
> 현재는 "활용", "재사용"이라는 표현만 있어 *"제공된 엔진을 그대로 썼다"* 로 읽힙니다.
> 실제로는 엔진 코어를 두 군데 직접 수정했으므로 이를 드러내야 합니다.

#### 제목 수정

| | 문구 |
|---|---|
| 현재 | CraftEngine의 Level / Actor 구조를 **활용해** 게임 구성 |
| 변경 | **학습한 CraftEngine 구조를 재사용하고, 필요한 기능은 직접 보완** |

#### 하단 요약문 수정

| | 문구 |
|---|---|
| 현재 | 학습한 Engine / Level / Actor 구조를 재사용하여 게임을 제작했습니다. |
| 변경 | 학습한 Engine / Level / Actor 구조를 재사용하되, **필요한 기능은 엔진에 직접 추가하고 코어 결함은 수정**했습니다. |

#### 좌측 카드 `CraftEngine · 학습한 프레임워크` — 재구성

현재 `Engine → Level → Actor` 3단만 있고 **아래 절반이 비어 있습니다.** 그 공간을 활용합니다.

**상단** (기존 3단 유지 + 모듈 한 줄 추가)

```
Engine  ──→  Level  ──→  Actor

Physics · Render · Input · Math
(스윕 AABB 충돌 / 콘솔 렌더러)
```

> `Physics`와 `Render`를 넣는 이유: 뒤에 나오는 트러블슈팅 07·08이 모두
> Render와 Physics의 경계 문제이므로, 구조도에 두 모듈이 있어야 연결됩니다.

**하단** (신규 블록 — 시각적으로 구분되게, 예: 구분선 또는 다른 배경 톤)

```
★ 직접 보완한 것

Engine    보조 레벨 오버레이 API 추가
          SetSecondaryLevel / SetSecondaryLevelActive
          Engine.h +30줄 · Engine.cpp +48 −13줄

Actor     생성자 previousPosition 초기화
          엔진 코어 버그 · 1줄
```

#### 우측 카드 `PolarRunner · 실제 구현` — 목록 수정

**현재 목록이 실제 코드와 다릅니다.**

| | 현재 슬라이드 | 실제 코드 |
|---|---|---|
| Level | TitleLevel, PolarLevel, MenuLevel (3개) | + **TestLevel** (총 4개) |
| Actor | Player, Enemy, Bullet, Obstacle (4개) | Player, Enemy, **PlayerBullet**, **EnemyBullet**, PolarObstacle, **PolarStar** (총 6개) |

**`PolarStar`(별) 누락이 특히 문제입니다.** 슬라이드 2에서 "별을 수집해 Enemy와 전투"가
핵심 루프라고 소개해놓고 구조도에 별이 없으면 질문을 유발합니다.

변경 후:

```
Level  (4)                 Actor  (6)

TitleLevel                 Player
PolarLevel                 Enemy
MenuLevel  ★               PlayerBullet · EnemyBullet
TestLevel                  PolarObstacle
                           PolarStar
```

- `MenuLevel`에 **★ 표시** — 슬라이드 8에서 자세히 다루는 대상임을 시각적으로 연결
- `TestLevel`은 사격 검증용 테스트 레벨(타이틀에서 `T` 키 진입). 테스트 방법을 보여주는 소재이므로 포함

#### 하단 기술 칩 수정

- `C++` 칩이 `C+` / `+` 두 줄로 쪼개져 있음 → **칩 폭을 늘리거나 자동 줄바꿈 해제**
- `CraftEngine` 칩은 좌측 카드 제목과 중복 → 삭제하고 `C++20`처럼 버전 표기로 대체 권장

#### 스피커 노트 (교체)

> 교육 과정에서 학습한 CraftEngine의 Engine / Level / Actor 구조를 그대로 재사용했습니다.
> 다만 그대로 쓰기만 한 것은 아니고, 일시정지 메뉴를 구현하면서 엔진에 보조 레벨 오버레이
> 기능을 직접 추가했고, 개발 중 발견한 Actor 생성자의 초기화 누락 버그도 엔진 코어에서
> 수정했습니다. 두 가지 모두 뒤에서 자세히 말씀드리겠습니다.

### 슬라이드 6 — 코스 진행 로직

#### 🔴 빈 박스 채우기 (최우선)

**슬라이드 중앙의 큰 검은 박스 2개가 비어 있습니다.** (파일 검사 결과 이미지 0개)
캡션 `> 0–1500m · 달리기`, `> 3500m+ · 전투`만 있고 게임 스크린샷이 들어가 있지 않습니다.
화면의 절반을 차지하는 영역이라 발표에서 가장 먼저 눈에 띕니다.

→ **해당 구간의 게임 플레이 스크린샷 2장을 넣어야 합니다.** (작성자가 캡처 제공 필요)

#### 원근감 설명 보강 (반복 질문 대응)

현재 우측 설명은 이게 전부입니다:

> Near / Mid / Far — 넓은 도로·큰 오브젝트 / 중간 폭 / 좁은 도로·작은 오브젝트
> 화면의 Y 위치를 기준으로 도로 폭과 X 오프셋을 계산해 원근감을 표현

**결과만 있고 방법이 없습니다.** "Y 기준으로 계산한다"는 사실상 동어반복이라
청중에게 "그래서 어떻게?"가 남고, 이 질문이 반복해서 나오고 있습니다.

→ 아래 코드 블록과 한 줄 설명을 추가합니다.

```cpp
normalized  = 1.0f - distance / viewDistance;
perspective = std::pow(normalized, 1.55f);   // 비선형 압축
```

> 선형 매핑이면 원근감이 생기지 않습니다.
> 지수 **1.55**로 지평선 근처는 촘촘하게, 발밑은 성기게 배치했습니다.

#### 문구 수정

- 흐름도 마지막 박스 `5000m Goal` → **`[코스거리] Goal`**

### 슬라이드 7 — Enemy 동작 로직

#### 🔴 코드 오타 수정 (필수)

슬라이드에 적힌 코드가 **C++ 식별자로 성립하지 않습니다.** (하이픈 포함)

```cpp
bool sc-camel-facing-left = side == EnemySide::Right;   // ❌ 현재 슬라이드
```

실제 코드 (`PolarRunner/Actor/Enemy.cpp:44`):

```cpp
const bool facingLeft = side == EnemySide::Right;       // ✅ 이렇게 수정
```

맞춤법 검사기가 `facingLeft`를 변환한 것으로 보입니다.
C++ 발표에서 컴파일되지 않는 코드가 화면에 뜨면 신뢰가 크게 깎이므로 반드시 수정하세요.

같은 슬라이드의 아래 줄도 함께 확인:

```cpp
Draw(facingLeft ? "<==_O_|" : "|_O_==>");
```

### 슬라이드 8 — Level 구조 개선 ★ 최우선

> **내용은 정확하지만, 이것이 "엔진을 직접 수정한 결과"라는 점이 드러나지 않습니다.**
> 현재는 제목이 "Level 구조 개선"이고 "Engine이 두 Level 관리"라고만 되어 있어,
> 게임 쪽 설계를 잘한 것처럼 읽힙니다.
> 실제로는 `Craft::Engine`에 **API 4개를 추가하고 메인 루프 4군데를 수정**한 작업입니다.

#### 제목 보강

| | 문구 |
|---|---|
| 현재 | 게임 상태를 유지하는 Pause Menu Overlay 구조 구현 |
| 변경 | **엔진에 보조 레벨 기능을 추가해 Pause Menu Overlay 구현** |

#### 우측 카드에 추가

현재 우측 카드는 `Primary · PolarLevel` / `Secondary · MenuLevel` 두 줄만 있고
**위아래로 빈 공간이 많습니다.** 아래 내용을 추가합니다.

**(1) 엔진에 추가한 API**

```cpp
// Craft::Engine 에 추가
template<typename T, typename ...Args,
    typename = std::enable_if_t<std::is_base_of<Level, T>::value>>
void SetSecondaryLevel(Args&& ...args);

void SetSecondaryLevelActive(bool active);
```

**(2) 메인 루프 변경 요약 (한 줄)**

> `Tick`은 보조 레벨이 활성이면 메인을 건너뛰고, `Draw`는 메인을 먼저 그린 뒤 보조를 겹칩니다.
> `OnInitialized` / `BeginPlay` / 액터 생명주기 처리 4군데도 두 레벨을 나란히 처리하도록 수정했습니다.

**(3) 강조 문장**

> 메뉴를 화면에 그리기만 한 것이 아니라, **보조 레벨도 완전한 Level로 동작**합니다.

(`문제 / Pause 메뉴로 / PolarLevel 책임 증가 → 개선 / 게임 상태와 UI Level의 / 책임 분리`)

### 슬라이드 9 — 문제 해결 07 (IceWall)

> 현재 슬라이드는 **가로(X) 좌표계 통일**만 다룹니다.
> 세로(깊이) 방향 충돌 판정 설명이 덱 전체에 없어서 이 질문이 반복해서 나오고 있습니다.
> 게다가 `Y = Draw 기준 행` vs `Y = Collision 기준 행` 도식 때문에
> **"세로도 좌표 비교로 하는구나"** 로 오해하기 쉽습니다. 실제로는 겹침이 아니라 통과 판정입니다.

#### 추가 — 충돌 판정 3층 구조

| 축 | 판정 방식 | 사용하는 좌표 |
|---|---|---|
| **가로 (X)** | 화면 좌표 **겹침** 비교 | 화면 X (Draw와 동일 계산) |
| **세로 (깊이)** | 행 **통과** 스윕 테스트 | 화면 Y |
| **높이 (점프)** | **논리 높이** 임계값 | 0.0 ~ 1.0 논리값 |

```cpp
// 이전 프레임 ~ 현재 프레임 사이에 플레이어 발밑 행을 지났는가 (swept row test)
const bool crossedPlayerRow =
    previousObstacleScreenY <= currentPlayerScreenY
    && obstacleScreenY      >= currentPlayerScreenY;
```

> 겹침으로 판정하면 진행 속도가 빠를 때 한 프레임에 여러 행을 건너뛰면서 충돌을 놓칩니다.
> 정수 화면 좌표는 손실 압축이라 역변환 왕복도 신뢰할 수 없어, **"그 행을 지났는가"** 라는
> 화면 기준 질문으로 바꿨습니다.

> 점프 통과를 화면 Y로 판정하지 않는 것이 핵심입니다. 화면 Y에는 거리 투영과 점프 높이가
> 섞여 있어서, IceWall의 높은 그림이 점프한 펭귄과 화면에서 겹쳐 보여도 실제 진행 거리는
> 아직 멀 수 있기 때문입니다.

> 분량이 부담되면 **표 3줄만** 넣어도 효과가 있습니다.

## 4. 신규 슬라이드 (권장)

### 신규 A — Enemy·맵 구성 (슬라이드 6과 7 사이 권장)

> 게임을 어떻게 구성했는지, 특히 **Enemy 등장 규칙과 맵의 관계**를 설명하는 슬라이드입니다.
> 현재 덱에는 Enemy의 *동작*(상태 머신, 슬라이드 7)은 있지만
> *언제 어떤 조건으로 등장하는지*가 없습니다.

**제목**: `진행 거리에서 파생되는 맵 · 장애물 · Enemy`

**좌측 — 파생 구조**

```
traveledDistance  ─ 단일 진실
   │
   ├─→ roadSlices[]     지형 · 도로 폭 · 커브      (시작 시 1회 구축)
   ├─→ obstacles[]      3레인 배치                 (시작 시 1회 배치)
   ├─→ stars[]          장애물 없는 레인에만       (시작 시 1회 배치)
   └─→ EnemyZone[15]    구간 진입 시 등장          (런타임 판정)
```

> 앞의 셋은 **정적 데이터**(시작할 때 모두 생성), Enemy만 **런타임 이벤트**입니다.

**우측 — Enemy 생명주기**

```
        Enemy 구간 진입
              │
              ▼
      ┌── 조건 5개 검사 ──┐
      │ 활성 Enemy 없음?   │
      │ 지형 == Coast ?    │──No──→ 구간 스킵
      │ SHOT > 0 ?         │        (index++ 만)
      │ 얼음길 220m 밖?    │
      └─────────┬──────────┘
                │ Yes
           경고 2초
                │
      SPAWN ── 바다가 그려진 쪽에서
                │
   Approaching → ClosingSide → Chasing
                │
      ┌─────────┴─────────┐
    격추      Coast 이탈    얼음길 전 후퇴
                          (탄환도 함께 정리)
```

**하단 요약문**

> 리스폰 타이머가 아니라 **거리 구간 15개**로 등장을 관리하며, 조건을 만족하지 못하면 그 구간은 건너뜁니다.

**핵심 설계 원칙 3가지** (강조 박스로)

1. **이길 수 없는 전투를 만들지 않는다** — SHOT이 0이면 Enemy가 아예 스폰되지 않음
2. **랜덤이지만 항상 통과 가능하다** — 3레인 중 안전 레인을 반드시 남기고, 별도 안전 레인에만 배치
3. **맵이 이벤트를 허용한다** — Enemy가 지형을 바꾸는 것이 아니라, `Coast` 지형일 때만 Enemy가 등장

> 세 가지 모두 **"랜덤 요소를 넣되 플레이어가 억울하지 않게"** 라는 하나의 원칙입니다.

### 신규 B — 트러블슈팅 09: 엔진 코어 버그 (슬라이드 10 뒤 권장)

> **"엔진을 어떻게 보완했는가" 피드백에 대한 가장 강력한 답입니다.**
> 기존 트러블슈팅이 07(게임 로직 좌표계) / 08(데이터 구조·책임)인데,
> 여기에 **엔진 코어**가 더해지면 문제 해결의 세 층이 완성됩니다.

**제목**: `엔진 코어의 초기화 누락을 찾아 수정`

**증상**

> 적이 근처에 오지도 않았는데 `CRASH: HIT BY ENEMY BULLET` 발생.
> 오른쪽에서 스폰될 때 유독 자주 발생.

**원인**

> `Craft::Actor` 생성자가 `previousPosition`을 초기화하지 않아 기본값 `(0,0)`으로 남아 있었습니다.
> 충돌 판정은 이전 위치와 현재 위치를 잇는 **스윕 선분**을 사용하기 때문에,
> 스폰 첫 프레임에 `(0,0)`부터 실제 스폰 좌표까지 **화면을 가로지르는 거대한 판정 선분**이 생겼습니다.
> 오른쪽에서 스폰될수록 이 선분이 플레이어를 지나갈 확률이 높아 증상이 한쪽에 몰렸습니다.

**해결 — 1줄**

```cpp
Actor::Actor(const std::string& image, const Vector2& position, Color color)
    : image(image), position(position),
      previousPosition(position),        // ← 추가
      color(color), width(static_cast<int>(image.size()))
{
}
```

**의미** (강조)

> 증상은 "적 탄환 버그"였지만 원인은 **엔진 코어의 초기화 누락**이었고,
> 같은 스윕 판정을 사용하는 **모든 스폰 프레임 충돌**에 잠재적 영향이 있었습니다.
> 좌우 발생 편차라는 단서를 따라 좌표 `(0,0)`을 의심한 것이 해결의 열쇠였습니다.

**하단 요약문**

> 07은 좌표계 문제, 08은 데이터 구조 문제, 09는 **엔진 코어 문제**였습니다.

## 7. 참고 — 자주 나오는 질문과 답변

발표 후 질의응답 대비용입니다. 슬라이드에는 넣지 않아도 됩니다.

### "원근감을 어떻게 만들었나요?"

> 거리를 화면 행으로 **비선형 매핑**했습니다. 선형이면 멀리 있든 가까이 있든 같은 속도로
> 다가와 원근감이 생기지 않습니다. 지수 1.55로 지평선 근처는 촘촘하게, 발밑은 성기게
> 배치했습니다. 도로 폭도 같은 깊이 값으로 스케일해서 지평선에서는 반폭 2칸,
> 발밑에서는 화면의 38%까지 벌어집니다.

### "왜 하필 1.55인가요?"

> 수학적 근거가 아니라 플레이 감각 기준으로 튜닝한 값입니다. 1.0이면 선형이라 원근감이 없고,
> 너무 크면 장애물이 갑자기 튀어나와 반응할 시간이 없습니다.

### "커브는 어떻게 처리했나요?"

> 처음에는 전역 커브 값을 모든 행에 동일하게 적용했는데, 폭이 2칸뿐인 지평선 행이 좌우로
> 크게 흔들려 도로가 접히는 문제가 생겼습니다. 그래서 행마다 자기 거리를 역산해 그 지점의
> 코스 데이터를 직접 샘플링하고, 먼 행의 횡이동은 smoothstep(`depth² × (3 − 2·depth)`)으로
> 억제했습니다.

### "세로 충돌은 어떻게 처리했나요?"

> 세로는 "겹쳤는가"가 아니라 **"통과했는가"**로 판정합니다. 장애물의 이전 프레임 행과
> 현재 프레임 행 사이에 플레이어 발밑 행이 들어있으면 충돌입니다. 겹침으로 판정하면
> 진행 속도가 빠를 때 한 프레임에 여러 행을 건너뛰면서 충돌을 놓칩니다.

### "왜 AABB 겹침을 쓰지 않았나요?"

> 정수 화면 좌표가 손실 압축이기 때문입니다. 화면 행을 거리로 역변환해 비교하는 방식을
> 먼저 시도했다가 실패했습니다. 투영 결과가 `static_cast<int>`로 잘려서, 역변환한 거리와
> 실제로 그려지는 행의 경계가 맞지 않아 충돌을 놓쳤습니다.

### 장애물별 통과 조건

| 장애물 | 통과 조건 | 이유 |
|---|---|---|
| `LowSpike` | 논리 높이 ≥ 0.4 | 낮은 가시 |
| `Puddle` | 논리 높이 ≥ 0.25 | 더 낮음 |
| `BrokenBridge` | 뜬 상태면 통과 | 구멍은 넘을 물리적 높이가 없음 |
| `IceWall` | 통과 불가 | 좌우 회피만 가능 |

### 코드 관련 주의

`nonShotCount`는 **SHOT 보유 수**를 담는 변수이지만 이름이 "non-shot"으로 읽힙니다.
코드를 보여주는 슬라이드에 이 변수가 등장하면 질문이 나올 수 있으므로,
슬라이드에서는 `shotCount`로 표기하거나 실제 코드를 리네임하는 것을 고려하세요.
